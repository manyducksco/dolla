# 5.0.4

Most of this release improves hot module replacement during development. Production builds get smaller and effects run faster.

## Features

- **More export forms hot reload.** Views are replaced in place when exported as `export default () => ...`, `export default Home` or `export { Home, Settings as SettingsPage }`, and stores exported as `export default AuthStore` or `export { AuthStore }` keep their instance. See [Views](../hmr.md#views) and [Stores](../hmr.md#stores).
- **Views held by other exports update.** A view captured by a sibling export, such as `export const routes = [{ view: Home }]`, now updates when you edit it. Before, the route kept rendering the old version. See [Views](../hmr.md#views).
- **Styled components keep their identity across reloads.** Modules that import one keep using the same component, and both mounted and newly mounted elements get the new styles. See [Styled components](../hmr.md#styled-components).
- **Changed constants reach the modules that import them.** Editing an exported string, number, plain object or array re-runs its importers, and the terminal logs which export changed (`hmr invalidate /src/config.ts export API_URL changed`). Before, importers kept the old value and nothing was logged. See [Changed values](../hmr.md#changed-values).
- **Reloads that reach no view are reported.** When an edited store or function has no mounted views, the console says so, and that running store instances keep the old code until their provider mounts again.

## Fixes

- **Stores survive a hot reload of the view that provides them.** The store kept its state, but its effects stopped and its cleanup hooks ran. A store the new version of the view no longer adds is now cleaned up.
- **Private stores in modules without semicolons keep working after a reload.** They failed with "Store is not provided by this context".
- **Modules with their own `import.meta.hot.accept()` work.** The plugin added calls to its helpers without importing them.
- **A comment mentioning `import.meta.hot.accept(` no longer turns off HMR for its module.**
- **A module that throws while reloading reports only its own error.** A `TypeError` from the HMR runtime was reported on top of it.
- **A hot-replaced view that throws while mounting leaves no partial DOM behind.**
- **No page reload on the first dev start** in setups where Vite discovers the HMR runtime late, such as `optimizeDeps.holdUntilCrawlEnd: false`.
- **The Vite plugin no longer runs under Vitest**, where it wrapped every exported function in your tests.

## Improvements

- **Smaller production bundles.** The CSS engine, the HMR runtime and debug-only work are left out of production builds that don't use them.
- **Importing dolla has no side effects.** `@manyducks.co/dolla` can be imported without a DOM, for example in Node.
- **Faster effects.** Running an effect does less work, and signal debug names are only built when an error is reported.

## Internal API changes

These only affect code that uses `@manyducks.co/dolla/internals` or wires up HMR by hand. See [Manual API](../hmr.md#manual-api).

- **`ViewNode.replaceView(view)` moved** to `replaceView(node, view)` in `@manyducks.co/dolla/hmr`.
- **Without the Vite plugin, import `@manyducks.co/dolla/hmr` before mounting anything.** Views mounted before the import aren't tracked for replacement. The plugin adds the import for you.
- **`__dolla_apply` takes an optional third argument**, the module's `import.meta.hot`, which it uses to invalidate importers when an exported value changed.

## Upgrading

Update the package. The Vite plugin and the HMR runtime ship together and should be the same version. Apps that use the Vite plugin need no other changes.
